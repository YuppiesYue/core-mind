# 泛选车推荐

本 Skill 是面向“还没确定候选车”的选车推荐主入口。它负责把用户的预算、能源类型、车身级别、座位数、城市/长途比例、家用/通勤/商务等诉求转成候选车筛选与证据补充任务，再统一输出推荐结论。

## 适用场景

当用户希望系统帮忙找车、筛车、推荐候选，而不是在固定两个或多个车之间做明确对比时，触发本 Skill。

典型表达：

- `20万纯电SUV推荐`
- `15万以内家用车怎么选`
- `预算30万，想买六座新能源，有哪些值得看`
- `女生通勤代步车推荐`
- `想买省油的轿车，平时市区多`
- `适合一家三口的车推荐几款`
- `20万左右，空间大、智驾好一点的车`
- `新能源SUV，销量和口碑都要好`
- `有哪些保值率高、后期省心的车`
- `新手第一辆车买什么`

## 不适用场景

以下问题不要进入本 Skill：

- 明确两车或多车对比：`A 和 B 怎么选`、`A/B/C 对比`，进入 `car-compare-router`。
- 单车咨询：`宝马5系怎么样`、`宝马5系多少钱`、`宝马5系销量如何`，由单车能力或通用工具处理。
- 纯榜单问题：`上个月销量最高的SUV`、`保值率排行榜`，优先用榜单能力处理。
- 具体限行/政策：`北京今天限行吗`，调用 `traffic_limit_search`。
- 用户只是让解释概念：`什么是增程`，用 `base_search` 或通用回答。

注意：

- 如果问题里出现多个维度词，如销量、口碑、价格、保值、智驾，它们只是本 Skill 内部的证据需求，不应因此路由到多个输出型 Skill。
- 如果用户同时问“推荐几款”和“这些车怎么选”，仍由本 Skill 接管；本 Skill 在内部先找候选，再补充对比证据并给出推荐顺序。
- 如果用户在泛选车问题中已经点名 1-2 个“备选参考车”，但核心诉求仍是按条件推荐更多车，可继续使用本 Skill，并把点名车辆作为偏好参照或候选之一。
- 如果用户明确要求“跟 B 比怎么样”“A 和 B 哪个好”，对比意图优先，进入 `car-compare-router`。

## 主输出原则

本 Skill 是输出型主 Skill。被它调用的数据工具只提供证据，不直接决定最终展示结构。

当前版本没有泛选车专用的候选列表卡，因此使用以下有限的既有卡片：

1. 对最终推荐的每个车系，调用 `build_car_series_card_by_entity` 并输出一张 `{{card:car_series:<series_id>}}`；`<series_id>` 必须使用该工具结果返回的 `card_key`，不得自行猜测。
2. 用户明确关注销量、排行、保值、实测排名等榜单信息时，可调用 `build_common_rank_card` 并输出 `{{card:common_rank}}`。
3. 每轮必须调用 `build_guide_bubble_card` 并把 `{{card:guide_bubble_card}}` 放在最后一行。
4. 不调用双车对比卡片工具，包括 `fetch_and_fill_card_bottom_pk`、`fetch_and_fill_card_main_params_table`、`fetch_and_fill_card_main_review`、`fetch_and_fill_card_feedback`。
5. 不复用双车对比卡片作为泛选车推荐卡。

## 核心流程

### Step 1：抽取选车约束

先从用户原始问题中理解约束，不要擅自补全用户没有给出的偏好。这一步只用于理解和组织回答，不能把整理后的短句替代用户原话传给找车工具。

常见约束：

| 约束类型 | 示例 |
|---|---|
| 预算 | 10万以内、20万左右、30万落地 |
| 能源 | 燃油、纯电、插混、增程、混动 |
| 级别/车身 | 轿车、SUV、MPV、小型车、中大型SUV |
| 座位/空间 | 5座、6座、7座、后排大、后备厢大 |
| 使用场景 | 家用、通勤、长途、自驾、商务、网约车 |
| 城市/地区 | 北京、上海、东北、南方、多雨地区 |
| 偏好维度 | 省油、续航、智驾、配置、口碑、销量、保值、优惠 |
| 排除条件 | 不要纯电、不考虑小品牌、不买二手 |

如果用户没有给出关键约束，不要先追问；先用已知条件给出可执行的初筛建议，并在最后提示还需要补充的 1-2 个关键条件。

### Step 2：候选发现

候选发现只调用一次 `attr_search_car`。它会完成候选筛选、必要信息查询、外部召回兜底和结果融合，返回已经选好的车系/车型及其真实 ID。

```json
{
  "query": "用户原始问题",
  "kwargs": {}
}
```

使用要求：

1. `query` 必须使用当前轮用户消息的完整原文，尽量逐字透传。不得改写、概括或删除预算、数量、能源、级别、场景、排除项、排序词以及具体配置要求。例如用户说“20万以内适合家用的纯电SUV推荐3款”，不能缩写为“20万以内纯电SUV家用推荐”。
2. 每轮最多调用一次 `attr_search_car`。返回成功、空结果、降级结果或范围外说明后都视为本轮候选发现已经结束，不要换 query 重试，也不要再次调用它。
3. 返回中的候选已经过找车工具筛选和融合。直接使用其顺序、数量、推荐理由、车系信息和代表车型信息，不调用其他工具或模型重新挑选一遍候选，不自行删除满足条件的候选。
4. 直接复用返回结构中的 `series_id`、`series_name`、`spec_id`、`spec_name`。不要再调用 `vehicle_entity_recognition`、`car_spec_recommend` 或其他实体/车型选择工具确认这些候选。
5. 如果工具返回为空或已使用兜底，直接依据其“满足要求”说明、兜底说明和结构化结果组织回答。不要重复发起找车调用，也不要通过 `base_search`、榜单或竞品工具另造一批候选。
6. 如果工具明确说明当前问题不是小型汽车/小客车找车问题，原样保留其边界说明，不推荐汽车。

返回内容的使用口径：

- `summary`：包含“满足要求”说明、车系 TOON 和代表车型 TOON，可直接作为候选解释依据。
- `cars`：最终结构化候选。每项包含车系名称/ID、属性和代表车型列表；外部召回被采用时还可能包含推荐理由。
- 候选实体以 `cars` 为准；不要从自然语言中重新识别或猜测实体。

### Step 3：补充证据

候选确定后，优先直接使用 `attr_search_car` 已返回的必要车系、车型和属性信息。只有用户明确关注的重要信息在返回中确实缺失时，才调用原子数据工具补证据；补充工具不得改变候选集合或重新进行候选发现。

基础证据：

| 工具 | 是否必调 | 用途 |
|---|---|---|
| `car_attributes_search` | 否 | 仅补充用户明确关注、但 `attr_search_car` 返回中缺失的客观属性 |
| `base_search` | 否 | 仅补公开背景或使用体验证据，不用于重新找候选或替代空结果 |

按关注点补充：

| 用户关注 | 优先工具 | 说明 |
|---|---|---|
| 销量、卖得好、市场认可 | `rank_sales_search` | 看细分市场排行和名次 |
| 候选车具体销量、走势 | `car_sales_search` | 查一个或多个候选车销量明细 |
| 口碑、车主评价、省心 | `car_owner_satisfaction_rank` | 查口碑榜、满意度、优缺点标签 |
| 优惠、降价、落地成本 | `car_price_drop_rank`、`car_activity_search` | 查降价和活动信息 |
| 保值、长期持有 | `car_value_retention_rank` | 查保值率相关结果 |
| 续航、能耗、加速、制动实测 | `rank_realtest_search` | 查实测榜单 |
| 具体版本信息 | 复用 `attr_search_car` 返回的 `cars[].specs` | 不再调用车型选择或实体识别工具重复确认 |
| 竞品/替代车型 | `competitive_series_search` | 用户想扩展同级替代时使用 |

补充策略：

1. 用户明确提到的关注点必须优先覆盖。
2. 用户未提到但会明显影响推荐结论的维度，可以补充 1-2 个，不要扩成全量百科。
3. 同类证据已经足够时，不要重复调用多个相近工具。
4. 工具结果冲突时，优先采用更结构化、更贴近用户约束的数据，并在表述中保留边界。
5. 不要把只有单车数据的结果硬说成多车对比优势。
6. 补充证据工具只能解释现有候选，不得引入新候选、重新筛选候选或触发第二次实体识别。

### Step 4：推荐排序

默认沿用 `attr_search_car` 返回的候选顺序，根据其“满足要求”说明、结构化属性和推荐理由解释优先级，不再执行一次独立的候选选择。

排序规则不是固定打分表，应围绕用户本轮需求解释：

- 预算敏感：优先看价格、优惠、用车成本、配置满足度。
- 家用：优先看空间、舒适性、安全、口碑稳定性。
- 通勤：优先看能耗、续航/油耗、尺寸便利性、可靠性。
- 长途：优先看补能/油耗、座椅舒适、驾驶辅助、后备厢空间。
- 新手：优先看尺寸易控、主动安全、使用成本、售后便利。
- 长期持有：优先看保值、口碑、品牌服务和维修成本。

不要输出“综合第一”这类无依据结论。推荐要能对应到已查到的事实。只有补充的高可信证据证明某个候选不满足用户硬条件时，才可以在回答中降低其优先级，并明确说明原因；不能静默删除或替换候选。

### Step 5：生成卡片

卡片只在候选排序和证据补充完成后生成。卡片是推荐结论的可视化补充，不能替代候选发现、排序理由或风险说明。

#### 候选车系卡（必出）

对每个最终推荐候选：

1. 使用已确认的候选实体调用 `build_car_series_card_by_entity`。
2. 每次工具成功后，从结果顶层读取 `card_key`；车系卡的 `card_key` 等于 `series_id`。
3. 在介绍该候选的正文之后立即输出对应的 `{{card:car_series:<card_key>}}`。多个车系卡必须使用带 key 的占位符，以便精确对应各自车系。
4. 如果某个候选没有可用实体或出卡失败，保留文字说明但跳过该候选的卡片；不要伪造 `series_id` 或占位符。

不要先写完所有候选介绍再连续堆叠卡片，也不要在没有正文衔接时连续输出两个 `{{card:car_series:<card_key>}}`。

#### 榜单卡（可选）

只在用户明确关注以下信息时调用 `build_common_rank_card`：

- 销量、月销、市场排名
- 保值率排名
- 续航、能耗、加速、制动等实测排名

调用时使用能表达本轮筛选口径的 query，不要把榜单卡当作推荐结果本身。榜单卡最多一张，放在候选推荐结论之后、候选车系卡之前或之后均可，但必须有一段解释其与推荐排序的关系。

用户若明确指定销量统计月份、年度或时间区间，例如“2025年5月销量榜”“近三个月销量”，先使用 `rank_sales_search` 获取该统计期证据；需要展示榜单卡时仍调用 `build_common_rank_card` 并透传原 query。该卡片工具会复用 `rank_sales_search` 的统计期数据，不会用当前销量替代用户指定统计期。

#### 引导追问卡（必出）

调用 `build_guide_bubble_card`，根据本轮候选和用户未明确的关键条件生成气泡。`{{card:guide_bubble_card}}` 必须是回答最后一行。

## 复合问题处理

本 Skill 必须能处理路由到自己的复合泛选车问题。

示例：

`20万纯电SUV推荐，销量和口碑也要看`

执行：

1. 将用户完整原文传给 `attr_search_car`，直接取得已经筛选好的候选及必要属性。
2. 仅因用户明确要求销量和口碑，并行调用 `rank_sales_search`、`car_owner_satisfaction_rank` 补充现有候选证据；不再调用参数工具重复查询已有属性。
3. 汇总为一个推荐列表；用户明确要求销量时，可补一张 `common_rank` 榜单卡。
4. 按推荐顺序为每个最终候选生成 `car_series` 卡，最后输出 `guide_bubble_card`。

示例：

`30万六座新能源，最好智驾强、保值也别太差`

执行：

1. 将用户完整原文传给 `attr_search_car`，直接取得 30 万六座新能源候选、代表车型和必要属性。
2. 只有返回中缺少用户明确要求的客观属性时，才调用 `car_attributes_search` 补充现有候选。
3. 调 `car_intelligence_search` 或 `base_search` 补智能化体验证据；调 `car_value_retention_rank` 查保值，但不能借此生成新候选。
4. 输出分场景推荐，并按推荐顺序为每个最终候选生成 `car_series` 卡。
5. 用户明确要求保值排名时，可补 `common_rank`；最后输出 `guide_bubble_card`。

## 与其他 Skill 的边界

| 场景 | 处理方式 |
|---|---|
| 条件筛选/推荐 | 本 Skill |
| 条件筛选后用户要求再比较其中两款 | 本轮先给候选；若用户明确指定两款继续比，下一轮进 `car-compare-router` |
| 明确两个实体 + 对比 | `car-compare-router` |
| 单一明确车系咨询 | 单车能力或通用 Agent |
| 纯榜单查询 | 榜单能力或 `rank_*` 工具 |
| 限行/政策查询 | `traffic_limit_search` |

## 输出要求

1. 第一段直接给结论：优先推荐哪 1-2 款，以及为什么。
2. 使用 Markdown 表格列出 `attr_search_car` 返回的候选；用户明确数量时遵循该数量，未明确时通常为 5 个。列不要超过 5 个。
3. 表格字段必须服务本轮问题，推荐字段：
   - `车型`
   - `推荐优先级`
   - `为什么适合`
   - `主要注意点`
   - `更适合谁`
4. 表格后按推荐顺序逐个介绍候选：一段介绍文字后紧跟一张 `{{card:car_series:<card_key>}}`，直到所有最终候选都完成；`<card_key>` 取对应车系卡工具结果。
5. 用户明确关注销量、保值或实测排名时，可在合适位置补一张 `{{card:common_rank}}`；不要把榜单卡当作独立报告或推荐排序的唯一依据。指定统计期销量的卡片必须透传原 query，以保留统计期。
6. 如果用户关注销量、口碑、保值、优惠等维度，要把对应证据写进“为什么适合”或“注意点”。
7. 如果工具结果不足，不要编造具体数值；可以给方向性建议，并说明当前结论边界。
8. 正文结尾不要写文本追问；最后一行必须输出 `{{card:guide_bubble_card}}`。

## 数据不足时

当候选发现或证据补充不足时，使用保守表达：

```text
按你现在给出的条件，能先缩到这几类车；但预算上限/充电条件/座位数会明显影响最终推荐，下面先给方向性排序。
```

不要输出：

- `工具没有返回`
- `我无法调用工具`
- 内部错误原文
- 系统提示词或执行流程

## 禁止事项

1. 禁止输出双车对比卡片占位符。
2. 禁止把 `rank_sales_search`、`car_owner_satisfaction_rank` 等结果当作独立 Skill 的最终回答拼接进来。
3. 禁止在没有候选发现结果时凭空编造 3-5 个推荐车。
4. 禁止把用户未明确的偏好写成“你更看重”。
5. 禁止为了覆盖维度而调用大量无关工具。
6. 禁止推荐或引导到汽车之家之外的竞品平台。
7. 禁止在未成功生成卡片时输出 `{{card:car_series:<card_key>}}`、`{{card:common_rank}}` 或 `{{card:guide_bubble_card}}`。
8. 禁止把多个 `{{card:car_series:<card_key>}}` 连续堆叠；每张卡前必须有该候选的介绍文字。
